# Honda 二輪 ECU 独自層：第2回 事実収集

対象リポジトリ：

1. sophienyaa/Honda-Motorcycle-ECU-Tools
2. andreibaw/Honda_K-Line_KWP2000

この文書では、上記2リポジトリから確認できる通信上の事実だけを整理する。
ソースコードの断片、識別子、コメント、README本文の引用・言い換えは含めない。
換算式については、リポジトリの実装から読み取れる式そのものだけを「実装からの推測」として記載する。

出所区分：

- 「実機ダンプ」：リポジトリに掲載されたECU通信データそのもの。
- 「実装からの推測」：実装がそのバイトをどう解釈・換算しているかから得られる事実。ECU内部仕様そのものとは区別する。
- 「記載なし」：対象リポジトリ内に該当する情報を確認できない。
- 「不明」：関連するデータはあるが、意味・単位・規則を確定できない。

## A. Table 0x11 の Fuel Inj

### A-0. Table 0x11 の実データ

CRF250L の Table 0x11 として、次の応答が掲載されている。

```text
13 19 71 11 00 00 1B 00 9E 3D 9E 3D 93 64 FF FF 69 00 00 00 80 57 28 80 B5
```

- 出所：sophienyaa/Honda-Motorcycle-ECU-Tools / Tables-With-Data-CRF250L
- 区分：実機ダンプ

この応答を先頭から0始まりで数えると、byte 18 = `00`、byte 19 = `00` である。

- 出所：同上
- 区分：実機ダンプ

### A-1. Fuel Inj の単位

- Table 0x11 の byte 18–19 は、CRF250L リポジトリのデータ記録上 `Fuel Inj` と記載されている。
- 単位は記載されていない。
- `ms`、`µs`、無次元などの単位を確定できる記載はない。
- CBR600RR側でも、対応する byte 18–19 は燃料関連の可能性がある未知値として扱われており、単位は確定されていない。

出所：
- CRF250L：Tables-With-Data-CRF250L
- CBR600RR：Table 0x10 通信例
- 区分：実機ダンプ／実機通信例に対する記載

結論：**不明。記載なし。**

### A-2. 生値から物理量への換算式

- CRF250L リポジトリには、byte 18–19 の `Fuel Inj` に対する換算式は記載されていない。
- 2バイトを1つの値として換算する処理も確認できない。
- CBR600RR側にも byte 18–19 に対する換算式はない。

結論：**記載なし。**

したがって、

```text
raw / 256 = ms
```

という換算は、この2リポジトリからは確認できない。

### A-3. endian

- byte 18–19 が上位バイト→下位バイトなのか、下位バイト→上位バイトなのかを示す記載はない。
- 2バイト値として解釈する処理も確認できない。

結論：**不明。記載なし。**

### A-4. 1エンジンサイクルあたりの噴射回数

- Fuel Inj 値について、1回転あたりなのか、2回転あたりなのかを示す記載はない。
- 4ストローク1気筒エンジンとしての噴射回数を使った燃料量換算処理もない。

結論：**記載なし。**

### A-5. インジェクタ dead time

- Fuel Inj 値からインジェクタ開弁遅れを差し引く処理は確認できない。
- dead time の値も記載されていない。

結論：**記載なし。**

### A-6. 燃料消費量・燃費

- CRF250L リポジトリに、Table 0x11 の Fuel Inj を使って燃料消費量または燃費を算出する機能は確認できない。
- CBR600RR リポジトリにも、Table 0x10 の未知の燃料関連バイトを使った燃料消費量・燃費計算は確認できない。
- インジェクタ流量（cc/min等）の値は記載されていない。
- 燃圧の前提も記載されていない。

結論：**記載なし。**

## C. Table 0xD1

### C-0. CRF250Lの実機応答

```text
09 0B 71 D1 03 00 00 00 00 00 AE
```

- 出所：sophienyaa/Honda-Motorcycle-ECU-Tools / Tables-With-Data-CRF250L
- 区分：実機ダンプ

この記録では、

- byte 4 = `03`：Kickstand Down
- byte 5 = `00`
- byte 6 = `00`
- byte 7 = `00`
- byte 8 = `00`
- byte 9 = `00`：記録上、エンジンON/OFFに関連
- byte 10 = `AE`：checksum

とされている。

byte 5–8 の個別の意味は記載されていない。

### C-1. byte 4

CRF250Lの実機記録では、

```text
03
```

がKickstand Downと記載されている。

CBR600RR側ではTable 0xD1のbyte 4について、

```text
00 = In Gear
01 = Neutral/Clutch
03 = On kickstand
```

と扱っている。

- 出所：両リポジトリ
- CRF：実機ダンプ
- CBR：実装からの推測、および掲載通信例の意味付け

両者で `03` がサイドスタンド状態を表す点は一致する。

### C-2. byte 8 の各ビット

- CRF250Lリポジトリでは byte 8 のビット単位の意味は記載されていない。
- CBR600RRリポジトリでは、Table 0xD1のエンジン状態として別の1バイトを `0x01 = Running` と判定しているが、各ビットの意味は記載されていない。
- bit 3 が車速約15 km/hで立つ、bit 2が何を意味する、という情報は対象2リポジトリには記載されていない。

結論：**bit 3 / bit 2とも、この2リポジトリからは不明。**

### C-3. byte 9

ここは車種によってフレーム長・位置関係が異なる。

CRF250L：

```text
09 0B 71 D1 03 00 00 00 00 00 AE
```

では、

- byte 9 = `00`
- byte 10 = `AE`（checksum）

である。

CRF250Lのデータ記録ではbyte 9がEngine On/Offに関連するものとして記載されている。

CBR600RR：

```text
02 0A 71 D1 00 00 00 00 01 22
```

では、

- byte 8 = `01`：Engine Runningとして扱われる
- byte 9 = `22`：checksum

である。

したがって、**CBR600RRではbyte 9はデータフィールドではなくchecksum**。

MC52のbyte 9が何を意味するかは、この2リポジトリからは確定できない。

## F. 今回確認できたKeep-Alive

CBR600RRリポジトリでは、約2～3秒以内に有効な要求を行わないとセッションが維持されないとされ、実装上の周期は2000 msである。

- 出所：andreibaw/Honda_K-Line_KWP2000
- 区分：実装からの推測

Keep-AliveとしてTable 0x00を要求している。

要求フレームは、通常のTable全体読み出し要求形式とチェックサム規則から次の完全な5バイトになる。

```text
72 05 71 00 18
```

- 出所：andreibaw/Honda_K-Line_KWP2000
- 区分：実装からの推測
- 注意：この完全なフレームが実機ダンプとして掲載されているわけではない。

Table 0x00に対するECU応答の完全なバイト列は記載されていない。

結論：
- Keep-Alive要求：上記フレームを実装から導出可能
- 必要間隔：約2～3秒、実装周期は2秒
- ECUからのKeep-Alive応答：**記載なし**
- Keep-Alive応答の内容：**不明**

CRF250L側では、専用Keep-Aliveフレームおよびその応答は記載されていない。

## H. チェックサム

通常のTable要求・応答について、両リポジトリで8-bitの負加算によるチェックサムが確認できる。

```text
checksum = (- sum(all preceding bytes)) mod 256
```

したがって、

```text
sum(all bytes including checksum) mod 256 = 0
```

となる。

- 出所：両リポジトリ
- 区分：実装からの推測

CRF250LのTable 0x11：

```text
13 19 71 11 00 00 1B 00 9E 3D 9E 3D 93 64 FF FF 69 00 00 00 80 57 28 80 B5
```

では、末尾 `B5` がこの規則に一致する。

CBR600RRのTable 0x10：

```text
02 16 71 10 2A 30 D4 87 2C 87 9F 3C E0 5D FF FF 8E 7A 12 0A 80 52
```

では、末尾 `52` がこの規則に一致する。

## I. 応答長の扱い

CBR600RR側では、応答のbyte 1が全長を示す。

Table 0x10：

```text
02 16 71 10 2A 30 D4 87 2C 87 9F 3C E0 5D FF FF 8E 7A 12 0A 80 52
```

byte 1 = `16` なので、全長は22バイト。

Table 0xD1：

```text

```

byte 1 = `0A` なので、全長は10バイト。

受信側は先頭2バイトを取得し、byte 1の値に基づいて残りのデータ長を決定する。

- 出所：andreibaw/Honda_K-Line_KWP2000
- 区分：実装からの推測

CRF250Lの実機記録でも同じ位置に長さ値が存在するが、長さフィールドの意味を明示的に説明する記載は確認できない。

## K. 特に重要な結論

1. **今回の2リポジトリから、CRF250L Table 0x11 の Fuel Inj byte 18–19 を `ms` とする根拠は見つからない。**
2. **`raw / 256 = ms` という推定は、対象2リポジトリには記載されていない。**
3. Fuel Inj の2バイトを16-bit値として扱うこと自体が、対象2リポジトリには記載されていない。
4. Fuel Inj について、dead time、インジェクタ流量、燃圧、燃費計算、噴射回数の情報は対象2リポジトリにはない。
5. CRF250L Table 0x11 の byte 21 = `57`、byte 22 = `28`、byte 23 = `80` だが、これらの意味は記載されていない。
6. CRF250L Table 0x11 の既知データは、RPM、TPS電圧、TPS、ECT電圧、ECT、IAT電圧、IAT、MAP電圧、MAP、Battery Voltage、Speedまで。
7. 点火進角は対象2リポジトリからは特定できない。
8. Table 0xD1について、CRF250Lではbyte 9が状態関連データとして記録され、CBR600RRではbyte 9がchecksumになっている。**同じbyte番号に同じ意味を仮定できないことが実データから確認できる。**
9. Table 0x20 / 0xD0 はCRF250Lで実際に応答が記録されているが、内容の意味は公開されていない。
10. MC52 / CB250Rについては、対象2リポジトリからは情報を取得できない。
11. CBR600RRではTable 0x00がKeep-Alive用途に使われているが、ECUからのTable 0x00応答は記載されていない。
12. **今回指定された空白のうち、Fuel Injの単位・換算・endian・噴射回数・dead time・燃費計算、およびMC52固有情報は、対象2リポジトリだけでは埋まらない。**
