# 独自層実装の出所（クリーンルーム記録）

`src/probe.cpp` が実装する Honda 独自層について、**何を入力にし、何を入力に
しなかったか**の記録。実施した手順をそのまま書く。実施していない工程は書かない。

## なぜ必要か

独自層の解析には先行事例があり、そのうち 1 つは **GPLv3**。本リポジトリは PUBLIC
なので、仮に二次的著作物とみなされると `index.html` / `map.html` まで含めて
GPLv3 になる。

前提として、**ECU がどう応答するかは Honda の装置の振る舞いという事実**であり、
先行事例の著者が創作したものではない。事実は著作権の保護対象ではなく、相互接続の
ための情報については EU ソフトウェア指令や SAS Institute v. World Programming、
Google v. Oracle が明示的にこれを認めている。GPL は著作権の上に乗る条件なので、
保護される表現を取っていなければそもそも発動しない。

**したがって問題は法理ではなく立証にある。** 「事実しか取っていない」ことを
後から示すのが難しいから、手続きを踏んで記録を残す。

## 実際に行った手順

### 1. 収集（別系統）

**リポジトリの所有者が ChatGPT に対象リポジトリを読ませ、事実のみを抽出させた。**
実装を行う側（Claude）は上流のリポジトリを一度も参照していない。

収集させた範囲を明示的に限定した。

| 収集可 | 収集不可 |
|---|---|
| 線上のバイト列（CS を含む完全な形） | ソースコードの断片（1 行でも不可） |
| タイミング（ブレーク長・待ち・間隔・ボーレート） | 識別子（関数名・変数名・定数名） |
| チェックサムの計算規則 | ファイル構成・関数の分割のしかた |
| 応答フレームの構造 | コメントや README の文章の引用・言い換え |
| テーブル番号と各バイトの意味 | |
| 生値から物理量への換算式 | |

出力には、事実ごとに**出所（どちらのリポジトリか、実機ダンプか実装からの推測か）**
を付けさせ、**不明なものは推測せず「不明」と明記**させた。

結果は [`KLINE_PROPRIETARY.md`](KLINE_PROPRIETARY.md) としてリポジトリに置いてある。
**受け渡しは人間がこの 1 ファイルを介して行い、それ以外の経路は無い。**

### 2. 実装

**`KLINE_PROPRIETARY.md` だけを見て `src/probe.cpp` を書いた。** 上流のリポジトリ、
そのコード、その文章は一度も参照していない。ローカルに複製も存在しない。

実装の構成（コマンド振り分け、半二重エコーの処理、長さ前置の受信、フレーム組み立て）
は独自。プロトコルが形を決めている部分（チェックサムのループ、フレーム構造）は
他に書きようがない。

### 3. 独立検証

**受領した仕様書を鵜呑みにせず、記載された全フレームを自前で検算した。**
独自層のチェックサムは総和の 2 の補数なので、フレームが正しければ
**全バイトの総和が 0 になる**。これは外部の主張に依存しない自己検証になる。

結果は下記のとおりで、**これによって信用できる事実とできない事実が分かれた。**

## 独立検証の結果

16 フレームを検算した。**長さフィールドは 16/16 一致。** チェックサムは 10/16 一致。

### 一致したもの —— 事実として扱う

- **要求フレーム 6 種すべて**
  `FE 04 72 8C` / `FE 04 FF FF` / `72 05 00 F0 99` / `72 05 71 10 08` /
  `72 05 71 D1 47` / `72 05 71 00 18`
- 応答 `02 04 00 FA`、CRF の `0x70` `0x20` `0x61`

### CRF の 4 フレーム —— 先頭バイトの誤記と判定し、補正して事実として扱う

| | 記載 | 補正 | 補正後の総和 |
|---|---|---|---|
| CRF `0x00` | 先頭 `09` | `02` | `0x00` |
| CRF `0x11` | 先頭 `13` | `02` | `0x00` |
| CRF `0xD0` | 先頭 `01` | `02` | `0x00` |
| CRF `0xD1` | 先頭 `09` | `02` | `0x00` |

**検算の通った応答はすべて先頭が `0x02`。** 4 件が独立に同じ補正で一致するので
偶然ではない。長さフィールドが合っていることから、バイトの脱落ではなく
**値の誤記**と判断した。さらに `0x11`（補正後）と `0x61`（無補正で一致）が
同じ長さ `0x19` で同じ配置を持ち、相互に裏付けが取れる。

### CBR の 2 フレーム —— 値は信用しない

| | 残差 |
|---|---|
| CBR `0x10` の応答 | `0x0D` |
| CBR `0xD1` の応答 | `0x71` |

先頭は既に `0x02` で、自然な 1 バイト訂正では説明が付かない。これらは
**README に掲載された例**であって生キャプチャではないため、**個々のバイト値は
採用しない。** ただし長さフィールドは一致しており、**バイト位置の情報は別に
扱う** —— `0xD1` の index 4 が状態を表す点は CRF の実測（補正後
`02 0B 71 D1 03 …` ＝サイドスタンド）と一致するので、位置は 2 系統で裏が取れている。

## 実装が置いている前提

| | 扱い |
|---|---|
| 要求フレーム・CS 規則・長さ規則 | 事実（検算一致） |
| CRF 実測ダンプ（先頭補正後） | 事実（検算一致） |
| `0xD1` index 4 = 噛み合い状態 | 事実に近い（2 系統一致） |
| CBR `0x10` / `0xD1` のバイト値 | **仮説。位置のみ使い値は使わない** |
| `0x11` byte 18-19 = 噴射時間 | **仮説。単位・endian・スケール不明** |
| keep-alive `72 05 71 00 18` / 約 2 秒 | 出所のある推定 |
| **MC52 が独自層を喋ること自体** | **未検証。喋らない可能性がある** |

## この記録の限界

- **完全なクリーンルームとは書かない。** 実務の手続きには、渡す前に仕様書を
  保護対象の表現が混じっていないか点検する工程がある。ここではリポジトリ所有者が
  その役を兼ねている。事実どおり「収集は別系統、受け渡しは文書 1 本、点検は人間」
  と書くに留める
- 収集側（ChatGPT）は独立した第三者ではなく、依頼を受けて動いている
