はい。かなり重要な差が見えてきました。
以下は、指定された **2リポジトリだけ**を調査対象にし、コードそのものの表現・識別子・構成を仕様書へ持ち込まず、**ECU側の通信上の振る舞いとして記述できる事実**だけを整理したものです。

なお、特にCRF250L側は、リポジトリ内の「テーブル実測値」と、それを読むためのコードの対応が完全には一致していません。この場合は無理に辻褄を合わせず、**不明／矛盾あり**として残します。

# Honda 二輪 K-Line ECU 通信仕様・事実収集版

## 0. 出典

* **CRF250L系**

  * `sophienyaa/Honda-Motorcycle-ECU-Tools`
  * MIT License
  * リポジトリにはCRF250Lで取得したとされるテーブル応答データが掲載されている。([GitHub][1])
* **CBR600RR系**

  * `andreibaw/Honda_K-Line_KWP2000`
  * GPLv3

# 1. 物理通信

* K-Lineは単線半二重通信である。CRF250L側では **10400 baud** が使用されている。([GitHub][3])
  **出典： [CRF・コード推定]**

* CBR600RR側も **10400 baud** である。
  **出典： [CBR・コード推定]**

* CBR600RR側のシリアル形式は **8N1** とされている。([GitHub][4])
  **出典： [CBR・コード推定]**

* ECU初期化前にK-LineをLowに **70 ms** 保持する。([GitHub][3])
  **出典： [CRF・コード推定]、[CBR・コード推定]**

* Low解除後、High状態を **120 ms** 保持してから通信を開始する。([GitHub][3])
  **出典： [CRF・コード推定]、[CBR・コード推定]**

# 2. 初期化シーケンス

## 2.1 CRF250L

* CRF250L側のWake-upフレームは以下。

```text
FE 04 72 8C
```

**出典： [CRF・コード推定]** ([GitHub][3])

* Wake-up送信後、**200 ms** 待ってから初期化フレームを送る。([GitHub][3])
  **出典： [CRF・コード推定]**

* 初期化フレームは以下。

```text
72 05 00 F0 99
```

**出典： [CRF・コード推定]** ([GitHub][3])

* 初期化フレーム送信後、約 **50 ms** 待ってからECU応答を読み取っている。([GitHub][3])
  **出典： [CRF・コード推定]**

* CRF250L側では、初期化成功判定として受信バイト列全体の8-bit総和ではなく、実装上は総和が `0x6FB` になることを判定条件としている。([GitHub][3])
  **出典： [CRF・コード推定]**

* **初期化成功時の実際のECU応答バイト列は、このリポジトリからは確定できない。**
  `02 04 00 FA` がCRF250Lの実機応答だったという証拠は掲載されていない。
  **出典：不明**

---

## 2.2 CBR600RR

* CBR600RR側のWake-upフレームは以下。

```text
FE 04 FF FF
```

**出典： [CBR・通信例] / [CBR・コード推定]** 

* Wake-up送信後、**200 ms** 待つ。
  **出典： [CBR・通信例]**

* 初期化フレームは以下。

```text
72 05 00 F0 99
```

**出典： [CBR・通信例] / [CBR・コード推定]** 

* CBR600RRで期待される初期化応答は以下。

```text
02 04 00 FA
```

**出典： [CBR・通信例] / [CBR・コード推定]** 

* CBR600RR側では、この4バイトと完全一致した場合を初期化成功としている。([GitHub][4])
  **出典： [CBR・コード推定]**

### 重要な車種差

* **Wake-upだけでもCRF250LとCBR600RRで異なる。**

```text
CRF250L : FE 04 72 8C
CBR600RR: FE 04 FF FF
```

* 一方、初期化フレームは両者とも

```text
72 05 00 F0 99
```

で一致する。
**出典： [CRF・コード推定]、[CBR・通信例/コード推定]** ([GitHub][3])

# 3. フレーム形式

両リポジトリで確認できる通常のテーブル要求は、

```text
72 LL 71 TT CS
```

という5バイト構造になっている。

* `72`：要求側からECUへの宛先アドレス
* `LL`：パケット全長
* `71`：テーブル全体読み出し要求
* `TT`：テーブル番号
* `CS`：チェックサム

この構造はCBR600RR側で明示的に確認できる。
**出典： [CBR・通信例/コード推定]**

---

# 4. チェックサム

## 4.1 通常のテーブル通信

* 4バイトのヘッダ／データ部分の8-bit総和を取り、その2の補数相当をチェックサムとして付加する方式である。

すなわち、

```text
CS = (- Σ data[i]) mod 256
```

であり、受信側では、

```text
Σ 全バイト = 0 mod 256
```

となる。

**出典： [CRF・コード推定]、[CBR・コード推定]** ([GitHub][3])

* 例えばテーブル `0x10` の要求は、

```text
72 05 71 10 08
```

である。

* テーブル `0xD1` の要求は、

```text
72 05 71 D1 47
```

である。

---

# 5. 応答フレームの長さ

* 応答の2バイト目がパケット全長を示す。
  **出典： [CBR・通信例/コード推定]**

例えば、

```text
02 16 ...
```

の場合、全長は `0x16 = 22` バイト。

* したがって、受信側は先頭2バイトを取得した後、2バイト目の値から残りのバイト数を決定できる。([GitHub][4])
  **出典： [CBR・コード推定]**

* 最終バイトがチェックサムであり、それ以前の全バイトから計算したチェックサムと比較される。([GitHub][4])
  **出典： [CBR・コード推定]**

# 7. CBR600RR：換算式

* RPMは2バイト値をそのまま16-bit値として扱う。([GitHub][4])
  **出典： [CBR・コード推定]**

* TPS電圧、ECT電圧、IAT電圧、MAP電圧は、

```text
電圧 = raw × 5 / 256
```

で換算される。([GitHub][4])
**出典： [CBR・コード推定]**

* ECT温度、IAT温度は、

```text
温度[℃] = raw - 40
```

で換算される。([GitHub][4])
**出典： [CBR・コード推定]**

* TPSは、

```text
TPS[%] = raw / 16 × 10
```

として扱われている。([GitHub][4])
**出典： [CBR・コード推定]**

* MAPはraw値をkPaとして扱っている。([GitHub][4])
  **出典： [CBR・コード推定]**

* バッテリ電圧は、

```text
Battery[V] = raw / 10
```

である。([GitHub][4])
**出典： [CBR・コード推定]**

* 車速はraw値をkm/hとして扱っている。([GitHub][4])
  **出典： [CBR・コード推定]**

記録上の意味付け：

* `FF` → 不明

* `00` → 車速
* `00` → Fuel Inj
* `00` → Fuel Inj
* `80` → 不明
* `57` → 不明
* `28` → 不明
* `80` → 不明

([GitHub][5])

### インジェクタ開弁時間について

この記録だけから確実に言えるのは、

* フレームの **0-based byte 18**
* フレームの **0-based byte 19**

に相当する2バイトが、記録上 `Fuel Inj` とされていること。

すなわち、

```text
... 69 00 00 00 80 ...
       ↑  ↑
       │  └─ Fuel Inj
       └──── Fuel Inj
```

ではなく、正確なフレーム位置で書くと、

```text
byte 16 = 69
byte 17 = 00   ← Speed
byte 18 = 00   ← Fuel Inj
byte 19 = 00   ← Fuel Inj
byte 20 = 80
```

です。

**したがって「Table 0x11のFuel Injは2バイト、フレーム0-based位置18–19」というところまでは公開データから確認できる。**

一方、

* 16-bit値か
* endian
* 単位
* 1 countが何μsか
* 本当にインジェクタ開弁時間なのか

は、**この2リポジトリからは確定できない。**

これは今回かなり重要な「空白」として残すべきです。

# 15. Keep-Alive

ここは今回かなり面白いところ。

## CBR600RR

* セッション維持には **2～3秒程度ごとの通信が必要**とされている。
* 実装では **2秒周期**でTable `0x00` を要求している。([GitHub][4])

したがって、CBR600RRについてコードから導出できるKeep-Alive要求フレームは、

```text
72 05 71 00 18
```

である。

**出典： [CBR・コード推定]**

ただし、

> ECUから返ってくるTable 0x00の応答バイト列

はリポジトリには掲載されていない。

したがって、

```text
Keep-Alive request = 72 05 71 00 18
Keep-Alive response = 不明
```

とするのが正確。

### Keep-Aliveの「必要間隔」

* READMEでは **2～3秒**。
* 実装上の周期は **2000 ms**。

したがって、公開情報から確認できる範囲では、

> **約2秒周期で有効な要求を送ることでセッションを維持している**

とするのが適切。

---

## CRF250L

* CRF250L側の公開コードでは、Table 0x11と0xD1を連続して要求している。
* Table 0x11の要求間隔として50 msの待ちが存在する。
* Keep-Alive専用フレームを送っていることは確認できない。([GitHub][3])

したがって、

> **CRF250Lについて、専用Keep-Aliveフレームの内容およびセッション維持限界時間は不明。**

---

# 16. エラー／否定応答

ここは注意が必要。

## CBR600RR

実装ではECU応答について、

* 応答ヘッダが時間内に来ない
* 応答ボディが時間内に来ない
* チェックサム不一致
* 長さフィールドが不正

という状態を区別している。([GitHub][4])

しかし、これらは**診断ツール側が通信エラーとして分類しているだけ**であり、

> ECUがその場合にどんな否定応答フレームを返すか

を示す実機ダンプではない。

したがって、KWP2000標準の一般的な `7F` 系否定応答をこのHonda独自実装へ持ち込む根拠は、この2リポジトリにはない。

**結論：ECUの否定応答フレームは不明。**

# 20. CB250R / MC52 / 2018年式への適用について

この2リポジトリから **CB250R (MC52, 2018) の仕様を直接確定することはできない**。

特に、

```text
CRF250L
    ↓
CB250R
```

あるいは

```text
CBR600RR
    ↓
CB250R
```

という単純な互換性を仮定する根拠はない。

少なくとも今回確認できた範囲では、

* 10400 baud
* `72 05 71 TT CS` というテーブル要求形式
* 8-bit負加算チェックサム
* `72 05 00 F0 99` という初期化フレーム
* 70 ms / 120 msの初期化タイミング

については共通性がある一方、

**Wake-upフレームは既にCRF250LとCBR600RRで異なっている。**

したがってMC52については、

> 「共通プロトコルの候補はかなり強いが、車種固有部分は実機確認が必要」

という状態。

* 本当に開弁時間なのか

は不明。

ここは**今回の資料から取れる最も具体的な位置情報**。

### C. 未対応テーブル

応答しないのか、エラーを返すのか、何らかのダミー応答を返すのかは不明。

### D. ECUの否定応答

`7F` 系を含め、ECUから実際に返された否定応答フレームはこの2リポジトリでは確認できない。

---

## 結論

この2リポジトリだけから、かなり確度高く「仕様」として切り出せるのは、

```text
10400 baud / 8N1
↓
K-Line Low 70 ms
↓
High 120 ms
↓
車種固有 Wake-up
↓
200 ms
↓
72 05 00 F0 99
↓
ECU応答
↓
72 05 71 TT CS
```

という通信骨格と、

```text
CS = -Σ(previous bytes) mod 256
```

というフレームチェックサムです。([GitHub][3])

そして **CRF250LとCBR600RRでWake-upが違う**ことは、MC52を調べる上でかなり重要な警告材料です。

一方、今回ユーザーが特に欲しがっていた

* **Keep-AliveのECU→診断機応答**
* **未対応TableのECU応答**
* **否定応答**
* **MC52のTable番号**
* **MC52のTable 0x11相当データ**

は、この2リポジトリだけでは埋まりません。

特に `Fuel Inj` は **CRF250Lではフレームbyte 18–19に存在する、というところまでは拾えるが、それ以上を「噴射時間」と断定するのは危険**です。ここは実機ダンプを追加収集するのが筋です。
