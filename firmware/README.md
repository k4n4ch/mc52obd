# MC52 基板のファームウェア

基板は [`../hardware/`](../hardware/)。ESP32-S3-WROOM-1-N16R8 ＋ L9637D（K-Line）。

**環境は 2 つ。** 基板が届いた直後は `selftest`、そのあとは `explore` を使い続ける。

| 環境 | 用途 |
|---|---|
| `selftest` | **机上の自己診断。バイクに繋がない。** 12V と Mac だけで基板の健全性を測る。役目は 2026-09-15 に完了 |
| **`explore`** | **探索コンソール。標準層と独自層の両方。BLE 経由。これを使う** |
| `explore_ota` | `explore` と同じバイナリを OTA で飛ばすためだけのもの |

当初は `obd`（標準層）と `probe`（独自層）に分けていたが、**現場で焼き直さずに
往復できることが切り分けの速さに直結する**ため `explore` 1 本に畳んだ。

## 配線

**USB（IO19/20）は未接続。** 書き込みもシリアルも `J3`（圧入 5 極）から行う。

| `J3` | ネット | ESP32 | USB-UART 側 |
|---:|---|---|---|
| 1 | `GND` | — | GND |
| 2 | `TXD0` | IO43 | RX |
| 3 | `RXD0` | IO44 | TX |
| 4 | `EN_MCU` | EN | DTR（自動リセット用。無ければ手で GND に落とす） |
| 5 | `IO0` | IO0 | RTS（同上） |

K ラインは `KL_TX`=**IO17** / `KL_RX`=**IO18**（UART1 の既定ピン）。
`U3`（L9637D）は pin3=`3V3`（ロジック VCC）/ pin7=`VIN`（バス側 VS）/ pin6=`KLINE`。

```
pio run -e explore -t upload --upload-port /dev/cu.usbserial-XXXX
```

自動リセットを繋いでいないので、**書き込みモードへは手で入れる。**

```
1. IO0 を GND    2. EN を GND    3. EN 開放    4. IO0 開放
```

**`EN` を開放した瞬間の `IO0` の状態がラッチされる**ので、3 が終わるまで `IO0` は
GND に落としたままにする。

**「出力が静止している」でダウンロードモードを判定してはいけない。** フラッシュが
空のうちは ROM が `invalid header` を吐き続けるので静止＝成功だったが、ファームを
焼いた後は**起動しても静止する**（コマンド待ち）。**`?` を送ってメニューが返らない
こと**で判定する。

## OTA —— 通常はこちら

**有線が要るのは最初の 1 回だけ。** 以降は WiFi で飛ばす（実測 1.37MB を 48 秒）。

```
BLE で  wifi <ssid> <pass>     最大 4 件。家の WiFi とテザリングを両方入れておける
BLE で  ota on                 IP が返る（mDNS で mc52-explore.local でも引ける）
Mac で  pio run -e explore_ota -t upload --upload-port <IP>
```

- **SSID とパスワードはソースに書かない。** このリポジトリは PUBLIC なので、
  BLE で設定して NVS に置く。NVS は暗号化されていないので機密扱いのものは入れない
- **`WiFiMulti` が見えているものを自動で選ぶ。** 場所で設定を変えなくていい
- **既定で切。** `ota on` で明示的に有効化し、**再起動で戻る**。LAN に無認証の
  書き込み口を開き続けない
- **`J3` は最後の逃げ道として残す。** 壊れたファームを飛ばすと BLE も OTA も死ぬ

## `selftest` —— 役目は終わっている

**`HANDOFF.md` に数字だけ書いて一度も測っていなかった主張 3 つを測るためのもの。**
2026-09-15 に全部通ったので、通常は使わない（基板を疑うときだけ戻る）。
`k` 相当は `explore` にも入れてある。

### `k` — K ライン折り返し（最重要）

**基板上の `R7`（510Ω・`VIN`→`KLINE`）が K ラインのプルアップ**なので、`J1` の
`KLINE` を**未接続のまま** 12V を入れれば K は 12V に吊られる。`KL_TX` を Low に
すれば L9637D が K を引き下げ、`KL_RX` に返る。**TX→K→RX の一周が基板内で閉じる。**

つまり**バイクが無くても 3.3V 動作の合否が出る。** L9637D のデータシートは
VCC 3〜7V を設計保証としつつ**試験条件は 5V のみ**で、基板上で唯一ここだけが
机上で終わっていなかった（[`../hardware/README.md`](../hardware/README.md)）。

- **DC** … `TX=H → RX=1` / `TX=L → RX=0` なら経路が成立している
- **エコー** … 10400bps で 1024 バイトの疑似乱数を往復させ誤りを数える
- **速度余裕** … 19.2k〜115.2k まで上げる。10400 でぎりぎりなのか十分余裕が
  あるのかを分ける。**前者なら温度や個体差で落ちる**

### `f` — LittleFS

設計は「4KB たまるか 5 秒経過で周期追記」なので同じ 4KB 単位で測る。
空き容量から**バイナリ 0.32MB/時 で何時間記録できるか**を出す（主張は約 40 時間）。

### `b` — BLE

**既定（MTU 23・1M PHY）だと 1〜2KB/s で 1 時間ぶんの転送に 12〜25 分かかり実用外**、
MTU 247 ＋ 2M PHY で 20〜50KB/s、というのが設計時の見積もり。実測して確かめる。
`MC52-selftest` として広告するので Mac から受ける。

```
.venv/bin/python ../tools/bletest.py -d 30
```

**macOS は MTU も PHY もアプリから指定できない**（CoreBluetooth が決める）ので、
どちらの値も観測するだけ。**判断は実効レートで行う。** 記録 1 時間ぶん（バイナリ
0.32MB）の転送に何秒かかるかまで出す。

## `explore` が何をするか

**ELM327 では原理的に叩けない層を叩く。** 届かないのはハードウェアの不足ではなく
プロトコルインタプリタとしての制約で、3 点とも GPIO と UART を直接握れば越えられる。

| | Honda 独自層 | ELM327 |
|---|---|---|
| 起動 | K 線を **70ms Low** | fast init は 25ms 固定。任意長ブレークを出せない |
| フレーム | `72 05 71 TT CS` | 必ず `8N TA SA` を前置する |
| チェックサム | **総和の 2 の補数** | ISO 14230 の単純和 |

**土台に任意バイト列を置いてあるので、仮説が外れても焼き直しが要らない。**
`w` や `s` はその上に乗せた薄い層でしかない。

| 分類 | コマンド | |
|---|---|---|
| **土台** | `x <hex..>` | バイト列をそのまま送って返りを見る |
| | `X <hex..>` | チェックサム（総和の 2 の補数）を付けて送る |
| | `brk <ms>` | **K 線を任意の長さ Low に落とす** ← ELM327 にできない部分そのもの |
| | `baud <n>` | K ラインの速度を変える |
| 独自層 | `w` | 初期化（70ms ブレーク → ウェイクアップ 2 種 → `72 05 00 F0 99`） |
| | `s` | **テーブル `0x00`〜`0xFF` 総当たり。MC52 で最初にやること** |
| | `d` | `0xD1`。index 4 が噛み合い状態で、**比推定に欠けていた入力** |
| | `m` | `0x11` / `0x10`。センサ群と、**index 18-19 の噴射時間**（標準層に無い量） |
| | `t <XX>` / `ka <0\|1>` | 任意のテーブルを 1 回 / keep-alive の入切 |
| 標準層 | `o` | fast init して `0C` / `0D` を読む（**足場**） |
| 物理層 | `k` | K ライン折り返し。**車両に挿していない状態で配線を検証する** |
| 更新 | `wifi` / `ota` | 上記「OTA」を参照 |
| その他 | `time <unix>` | 壁時計を合わせる（GPS ログとの突き合わせに要る） |

**Mac 側は [`../tools/klconsole.py`](../tools/klconsole.py)。** BLE で繋いで素通しする
だけなので、基板側のコマンドを増やしてもこちらは直さなくていい。接続時に壁時計を
自動送信する。

**`x` / `X` は毎回エコーの一致を表示する。** K ラインは単線半二重で送信波形が RX に
戻るので、**それが物理層の健全性の指標になる**（配線の入れ違い、GND や 12V への短絡、
L9637D の不調が全部そこに出る）。車両の前で通信が通らないとき、基板側か車両側かを
切り分けられる。

**MC52 が独自層を喋ること自体が未検証。** ウェイクアップは CRF250L（`FE 04 72 8C`）と
CBR600RR（`FE 04 FF FF`）で既に違っており、MC52 がどちらでもない可能性がある。
だから決め打ちせず 2 種を試し、総当たりから入る。初期化の成功判定も緩くしてある ——
**MC52 が何を返すかが未知なので、決め打ちすると「応答しているのに失敗と判定する」事故になる。**

### 仕様の出所

**[`PROVENANCE.md`](PROVENANCE.md) に記録した。** 収集は別系統（ChatGPT）が行い、
受け渡しは [`KLINE_PROPRIETARY.md`](KLINE_PROPRIETARY.md) 1 本のみ。実装側は上流の
リポジトリ・コード・文章を一度も参照していない。

受領した仕様書は**鵜呑みにせず全フレームを自前で検算した。** 独自層のチェックサムは
総和の 2 の補数なので、正しければ全バイトの総和が 0 になる。**16 フレーム中 10 が一致、
CRF の 4 つは先頭バイトの誤記と判定して補正、CBR の 2 つは値を採用しない。**
何をどこまで信用しているかは `PROVENANCE.md` の表にある。

### 標準 OBD 層（`o`）—— 足場

ISO 14230-4 KWP **FAST** / 10400bps / テスタ `0xF1` / ECU `0x10`。
仕様は Track A（ELM327）の実測から（[`../FINDINGS.md`](../FINDINGS.md)「通信の同定」）。

fast init（25ms Low → 25ms High → StartCommunication）の後、`0C` と `0D` を
交互に読んでシリアルへ出す。K ラインは単線半二重なので**自分の送信がエコーで返る**。
それを読み捨てつつ、内容が一致するかを見ている。

**ここが通れば、ファームの土台（UART・タイミング・エコー処理）は正しいと分かる。**
独自層が無応答だったときに「実装が悪いのか MC52 が喋らないのか」を切り分けられる。
